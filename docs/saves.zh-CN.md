# 存档修复、存档位置与 Steam 云联接

[English](saves.md) · **简体中文**

修复游戏更新后打不开的 Ren'Py 存档，并让所有存档位置内容保持一致。

如果点存档格时游戏崩溃，报：

```
Exception: Couldn't find a place to stop rolling back.
Perhaps the script changed in an incompatible way?
```

这份文档就是解法。

---

## 快速开始

关掉游戏，然后运行：

```
savefix
```

这是只读的。它会打印每个存档和每个位置的状态，最后给出一段 **What to do**，直接写明下一步该跑哪条命令。你不需要自己判断该用哪个工具。

双击 `savefix.cmd` 效果一样，而且窗口不会自动关闭。

### 命令

| 命令 | 作用 |
|---|---|
| `savefix` | 检查所有存档和位置。安全，不写任何东西。 |
| `savefix fix` | 先备份，再修复所有损坏的存档。 |
| `savefix sync` | 先备份，再把当前存档复制到所有位置。 |
| `savefix backup` | 只备份，然后停止。 |

给 `fix` 或 `sync` 加 `--dry-run`，可以只看计划、不写入。

任何写入前都会自动备份，备份落在安装根目录下：`..\CSE-1.0-pc\_save_backup_<时间戳>_<原因>\`。

**恢复就是普通的文件复制。** 每个备份里都有一个 `WHERE.txt`，写明每个子文件夹来自哪里 —— 把文件拷回去就完成了。故意不提供 `restore` 命令：真需要恢复的时候，你应该亲眼看清自己在覆盖什么。

## 存档为什么会坏

Ren'Py 用一个三元组标识脚本里的每一条语句：

```
(filename, name_version, name_serial)
```

这些标识符被编进编译后的 `.rpyc` 文件里，存档的回滚日志（rollback log）保存它们来记住你玩到哪儿了。开发者为新版本重新编译脚本时，这些标识符会被重新生成。

于是旧版本的存档指向了已经不存在的语句。读档时 `RollbackLog.rollback()` 遍历整个日志，想找一条仍然存在于脚本中的语句，一条都找不到，一直走到末尾，就抛出上面那个异常。

**这不是存档损坏。** 你的剧情变量、旗标、进度全都完好 —— 坏掉的只是那些*书签*。

### 以 1.0 → 2.1.0 这次为例

- 旧存档引用的 `name_version` 是 **1771353428**。
- CSE 2.1.0 的章节脚本里是 **1771573257** / **1771573258**。
- 重合数量：**零**。开发者是从头重新编译的，所以每个 1.0 存档里的每个标识符都是死的，没有任何部分幸存。
- serial 也有偏移，但幅度很小，而且**不同区段偏移量不同**（在 `script_chapter_2.rpy` 的不同位置分别是 −9、0、+3）—— 这是插入和删除语句留下的特征，而不是整体重新编号。

## 修复原理

1. **用内容定位续玩点。** 存档里记录了最后显示的那句对白（`store._last_say_what`）。把这段文本拿去和已安装的脚本比对，唯一匹配就确定了你当时所在的语句，也就得到了 serial 偏移量。如果这句话不唯一，就用对白历史里前面的几句来从候选中挑出正确的那个。

2. **用历史交叉验证。** 存档历史里的每一句都用同样方式匹配，这些匹配结果必须是 **严格递增**的。如果不是，说明脚本的那一段被重构过，偏移量不可信。

3. **保守改写。** 只改写历史能够证实的那个窗口内的标识符，更早的标识符**故意留成死的**。一个死标识符只是限制你能回滚多远；而一个错误映射的标识符会把你丢到错误的行上。这就是为什么修好的存档回滚深度各不相同（`14/129`、`43/129`……）—— 那是安全余量，不是损伤。

4. **宁可拒绝，不去猜。** 如果某个 `call_location_stack` 条目落点不是一条 `Call` 语句，就直接跳过这个存档，而不是写入一个坏掉的返回栈。

5. **原地打补丁。** 在 pickle 里，version 是 4 字节的 `BININT`，serial 是 1/2/4 字节的 `BININT*`。替换时按相同字节宽度写入，所以什么都不会移位，pickle 的 memo 表依然有效，不需要重新 pickle。任何需要更宽操作码的改写都会被跳过，而不是去改变数据流长度。

6. **重新签名。** Ren'Py 用 `%APPDATA%\RenPy\tokens\security_keys.txt` 里的 ECDSA 密钥给日志签名。打补丁会让签名失效，之后 `check_load()` 会**静默**拒绝这个存档 —— 表现就是点存档格什么都不发生。工具会用你本机的密钥重新签名，和 Ren'Py 自己的 `upgrade_savefile` 做的是同一件事。

7. **验证。** 每个修好的存档都会被重新读取，并跑一遍 Ren'Py 读档时执行的那个检查，通过了才报告修复成功。

### 安全性

存档和 `.rpyc` 都是 pickle，而 pickle 是可以执行代码的。工具从不把它们交给标准 unpickler：`SafeUnpickler.find_class` 拒绝导入任何东西，只返回一个惰性的桩类，所以存档或脚本文件里的任何内容都无法运行。工具只从里面读数据。

## 存档位置

Ren'Py 会把存档放在多个地方，而 Steam 云同步的那个，未必是游戏真正读取的那个：

| 位置 | 角色 |
|---|---|
| `%APPDATA%\RenPy\SCR-1758907360\` | **实时目录。** 游戏真正读写的地方。 |
| `CSE-2.1.0-pc\game\saves\` | 镜像，当前安装。游戏也会往这里写。 |
| `CSE-1.0-pc\game\saves\` | 指向上一行的**联接（junction）**。Steam 云同步的是这个。 |
| `%APPDATA%\RenPy\SCR-1758907360\sync\` | Ren'Py Sync 暂存区，读档时不扫描。 |

> 联接建立于 2026-08-10，所以最后两行其实是同一个文件夹的两个名字。`savefix` 会
> 通过 `realpath` 识别出来，只列一次。

旧安装那个文件夹是个陷阱：CSE 2.1.0 从不读它，所以你把存档修好了，对 Steam 云里存的东西毫无影响。`savefix sync` 会把实时存档推到所有位置去，这才让云端那份副本有意义。

`savefix` 会自己找到这些位置 —— 包括脚本已被删光的旧安装 —— 所以上面这张表是背景知识，不是你需要动手处理的事。

### Steam 实际同步的是什么

App ID **4309030**，云根目录 `GameInstall`，只有一个文件夹：

```
<Steam>\steamapps\common\CSE-1.0-pc\CSE-1.0-pc\game\saves\
```

也就是 11 个存档格加一个 `persistent`。这个路径写死指向**旧**安装，从没为 2.1.0 的目录结构更新过，所以 Steam 同步的是一个当前版本既不读也不写的文件夹。

这一点你可以自己验证 —— Steam 把它跟踪的每个文件记录在：

```
<Steam>\userdata\<accountid>\4309030\remotecache.vdf
```

Steam 还会在它同步的文件夹里丢一个 `steam_autocloud.vdf` 标记文件，`savefix pull` 就是靠这个来识别它的。

## 双机游玩

因为 Steam 同步的文件夹游戏根本不读，这条链条从中间断开了，两端都需要手动复制一步：

```
   实时存档目录  %APPDATA%\RenPy\SCR-...     <- 游戏在这里读写
        ^  |                                    （两者之间没有任何连接）
        |  v
   Steam 云      CSE-1.0-pc\game\saves       <- Steam 在这里读写
```

### 手动做法

在刚玩完的那台机器上运行 `savefix sync`，然后退出 Steam 让它上传。到另一台机器上，等 Steam 下载完成后，把 `CSE-1.0-pc\game\saves\` 里的文件复制进 `%APPDATA%\RenPy\SCR-1758907360\`，然后开玩。

能用，但上传那一半在你下次开玩的瞬间就过期了，很容易忘。

### 联接（更好的做法）

`CSE-2.1.0-pc\game\saves` 是 Ren'Py 真正在读写的目录，游戏会自己保持它最新。所以把 Steam 那个文件夹做成指向它的联接，两边的手动步骤就都没有了：

```
mklink /J "<...>\CSE-1.0-pc\CSE-1.0-pc\game\saves" "<...>\CSE-1.0-pc\CSE-2.1.0-pc\game\saves"
```

`tools/make-junction.cmd`（Windows）和 `tools/make-junction.sh`（Linux/macOS + Wine）会替你完成这件事，包括自动定位安装目录、备份将被替换的文件夹，以及 `--dry-run` / `--undo`。在 Linux 和 macOS 上它们创建的是普通符号链接而不是联接：联接是 NTFS 的重解析点，而 Wine 前缀所在的文件系统不是 NTFS；Wine 会把符号链接目录以普通目录的形式呈现给 Windows 程序（Steam 也包括在内）。结果相同，机制正确。

> 两个脚本都写死了文件夹名 `CSE-1.0-pc`（Steam 的）和 `CSE-2.1.0-pc`（游戏的）。
> 下次游戏更新后，把脚本顶部的两个变量改成新的文件夹名即可 —— `.sh` 里是
> `OLD_REL`/`NEW_REL`，`.cmd` 里是 `OLD`/`NEW`。`savefix.py` 不需要改，它会自己
> 通配匹配现有的安装。

上传方向：Steam 永远看到最新存档，不需要再跑 `sync`。下载方向：Steam 下载下来的文件直接落在游戏本来就会读的文件夹里，存档自然就出现了。

操作时**必须关闭 Steam 和游戏**，先做备份，并且确认那个文件夹里当前是最新存档 —— 如果在它还装着旧存档时建立联接，Steam 第一次同步可能会把那些过期文件推回给你。

这里用联接是正确选择（`mklink /J`，不需要管理员权限）。关键在于它必须指向**镜像**，而不是 `%APPDATA%`。把 Steam 链到 `%APPDATA%` 等于把你的真正数据源接进了 Steam 的冲突解决逻辑，一次糟糕的下载 —— 或者一次会顺着链接删除的卸载 —— 就会带走你真正的存档。指向镜像则让 `%APPDATA%` 完全在 Steam 触及范围之外，最坏的情况也不过是一份可替换的副本出问题，跑一次 `savefix sync` 就能修好。

### 注意事项

- 在另一台机器上第一次读档会弹出 Ren'Py 的 **"unknown token"** 提示，因为存档是用原机器的密钥签名的。接受它，并接受"信任该密钥"的提议，之后就不会再问了。
- `persistent` 也会同步，所以解锁内容和图鉴进度会跟着走。
- 如果两台机器游戏版本不同，存档会显示为 `BROKEN`。跑 `savefix fix` 即可。这是预期行为，不是故障。
- 建立联接后，镜像目录里的崩溃转储（`_tracesave-*.save`，几百 KB）也会被一起上传。无害，可以放心删除。
- **在 CrossOver 下，`mklink /J` 建立的联接从 macOS 看是一个空目录** —— Wine 把重解析点存在 `user.WINEREPARSE` 扩展属性里（用 `xattr -l <目录>` 可以看到）。它对瓶子内的游戏和 Steam 都能正确解析。但如果在 macOS 上原生运行 `savefix`，它无法跟随这个链接，因此根本不会列出 `CSE-1.0-pc\game\saves` 这个路径 —— 它报告的是真正的那个文件夹，并正确标注 `<- Steam Cloud syncs this`，依据是透过链接落到那里的 `steam_autocloud.vdf` 标记。

### 存档通用说明

- **崩溃转储（`_tracesave-*.save`）会被忽略。** 它们是游戏抛异常时写的，不是存档点。但它们的时间戳对判断*什么时候*出的问题很有用。
- **自动存档会轮转。** `auto-1` … `auto-10` 会随着游玩不断前移，所以你在忙别的事情时，某个旧的自动存档点可能已经被挤出这个环了。
- **把存档搬到另一台电脑**会触发 Ren'Py 的 "unknown token" 提示，因为签名和本机密钥绑定。接受即可读档。没被修改过的存档也一样如此 —— 不是修复工具引入的问题。

## 出问题时

一切都可回退。备份就是普通文件夹装着普通文件：打开最近的 `_save_backup_*` 文件夹，读 `WHERE.txt`，把每个子文件夹里的文件拷回它写明的目录。真正重要的那个是 `Roaming-RenPy-SCR-1758907360` —— 那是实时存档目录。

### 常见情况

**"the ecdsa module is required"** —— 请运行 `savefix.cmd`，不要直接跑 `savefix.py`。启动器会用 `uv` 提供 `ecdsa`。没有 `uv` 的话，跑 `pip install ecdsa`。

**"cannot locate resume point"** —— 存档里最后那句对白在已安装的版本里找不到，通常是因为那场戏被重写或删掉了。工具会原封不动地放过这个存档，而不是去猜。什么都没丢，只是没法自动定位。

**`fix` 之后存档还是读不了** —— 恢复备份，并把情况反馈出来。工具在报告成功前会做验证，所以这种情况不应该悄无声息地发生。

**Steam 云覆盖了东西** —— 跑 `savefix` 看哪些位置不一致，然后 `savefix sync` 把实时存档推回去。处理期间先离线游玩，可以避免一次下载把你的成果冲掉。
